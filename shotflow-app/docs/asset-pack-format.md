# Stillmark 资产包容器规范 · ZIP v1

日期：2026-11-26。状态：`refactor/portable-agent` 开发分支已实现 ZIP v1 的项目/分镜导出、预检、暂存和原子导入；尚未合入 `main`。自动化覆盖不代表真实手机、超大包和外部 Agent 盲测均已验收。本文说明当前契约、实现限制和未完成的发布门禁。

## 1. 设计约束

- 本地优先：不要求账号、云端、模型服务或实时同步。资产包是用户主动传输的文件，不会自动上传或分享。
- 新的项目/分镜迁移包使用标准 ZIP；JSON 仅承载清单和业务数据，图片作为独立二进制条目。兼容现有旧版 JSON 导入；开发期 v5 JSON 原型不作为新的交换契约。
- 容器版本、业务数据版本、包类型和应用版本彼此独立。当前只接受已知容器/数据版本和 `projects`、`shots` 两种 kind；未知类型不得降级为整库恢复。
- 原有项目数据模型与 IndexedDB 不因迁移包而重写。完整备份仍是独立的 JSON 全库恢复路径，导入需单独确认。
- 包内容不加密、不签名。照片、拍摄地点、客户信息、预算和执行状态由用户决定是否纳入与分享；SHA-256 只用于完整性校验，不证明来源或真实性。

## 2. ZIP v1 格式

```text
session.stillmark.zip
├── manifest.json
├── data.json
└── images/
    ├── <sha256>.jpg
    └── <sha256>.png
```

ZIP 根目录只允许 `manifest.json`、`data.json` 和清单所声明的图片文件；ZIP 工具可以额外写入单个空 `images/` 目录项，其他目录项拒绝。不得加入重复路径、额外文件、加密条目、符号链接、嵌套归档或可执行内容。生产读取器允许已支持的 STORE/DEFLATE 压缩方法。

`manifest.json` 的正式结构见 [清单 Schema](../schemas/asset-archive-manifest-v1.schema.json)：

- `format`: 固定为 `stillmark.asset-pack`。
- `containerVersion`、`dataVersion`: 当前均为 `1`。
- `kind`: `projects` 或 `shots`，必须与 data.json 一致。
- `data`: 固定路径 `data.json`，带精确字节数和小写十六进制 SHA-256。
- `images`: 每个逻辑 key 的 ZIP 路径、MIME、字节数和原始文件 SHA-256。

`data.json` 的结构见 [数据 Schema](../schemas/asset-archive-data-v1.schema.json)，顶层字段为 `dataVersion`、`kind`、`entries`。`projects` 中每项是完整策划案；`shots` 中每项是承载所选分镜及依赖的项目对象。图片由 `refs[].key`、情绪板图片引用或分镜 `refIds` 使用逻辑 key 关联，不引用 ZIP 路径或运行时 IndexedDB key。

图片路径使用原始字节 SHA-256：`images/<sha256>.<ext>`。相同字节可以让多个逻辑 key 映射到同一 ZIP 条目，但清单需保留各自的 key。不同内容不得因尺寸或画面相似而合并。支持 MIME 为 JPEG、PNG、WebP、GIF 和 AVIF；禁止任意 SVG、HTML、远程 URL 和 Base64 图片字段。

## 3. 选择、导入与依赖语义

| `kind` | 导出入口 | 导入选项 | 导入结果 |
|---|---|---|---|
| `projects` | 看板多选完整项目 | 创建新策划案 | 追加新项目，不覆盖现有数据 |
| `shots` | 项目内独立于收藏的分镜多选 | 新建项目，或选择一个现有项目 | 新建时保留所选规划；追加时只写入分镜及其直接场景、图片依赖 |

分镜追加时，目标项目的名称、客户、概念、日程、预算、备注、既有分镜顺序和执行状态保留；新分镜追加至末尾，ID 与图片 key 重映射。同名场景不自动合并。仅合并所选分镜实际使用的日期和参考标签。目标在提交前消失或数据基线冲突时拒绝提交。

完整项目包包含项目的策划与执行状态、场景、日程、清单和关联图片，可能包含客户隐私。不要夹带无关项目、图库缓存、模型凭据或 API 密钥。外部图库引用必须随包提供合法且可离线使用的图片，否则应在交付前说明缺失。

正常导入先校验 ZIP 目录、清单、业务数据、引用闭包、大小和类型，再展示预览。用户确认前不写项目或图片。确认后图片逐个校验并暂存，随后在事务中比较基线、发布图片及项目并清理暂存。失败或取消不得覆盖已有项目；完整备份仍走单独的明确全量恢复入口。

## 4. 安全处理

- 拒绝绝对路径、`..`、反斜线、NUL、重复/归一化冲突路径、目录占位、符号链接、加密文件、不支持的压缩方法和未声明条目；不按归档路径写本地文件。
- 实际检查目录与解压字节数、CRC、本地头、条目重叠、JSON 摘要、图片 SHA-256、图片签名、可读尺寸和业务引用闭包。清单声明不能替代实际字节检查。
- 图片检查是轻量头部识别，不等同完整图片解码、内容鉴定或视觉相似度分析。AVIF 必须有可识别的尺寸元数据；无法确认尺寸的图片拒绝导入。
- 包内字段只按数据处理并经过应用净化，不执行文本、脚本或远程引用。外部 Agent 必须经由正常 UI 导入、预览、确认和持久化流程，不得直写 IndexedDB 或调用私有函数。

## 5. 当前运行时限制

| 资源 | 当前上限 |
|---|---:|
| ZIP 总大小 | 128 MiB |
| 解压总量 | 128 MiB |
| 单张图片 | 16 MiB |
| `data.json` | 16 MiB |
| `manifest.json` | 4 MiB |
| 唯一 ZIP 条目 | 10,000 |
| 逻辑图片映射 | 20,000 |
| 图片最大尺寸 | 每边 16,384 px，且不超过 40 MP |
| 单次目录/元数据读取 | 8 MiB |

这些是当前实现的资源保护上限，不是 ZIP 格式的永久限制，也不代表所有设备都能处理到上限。浏览器存储配额、内存和性能因设备而异。普通下载路径需要在完成后构造下载 Blob；支持安全上下文 File System Access API 的浏览器可选择直接写入文件句柄。两条路径都受 128 MiB 预算约束。

## 6. 实现与验收边界

当前分支包括固定版本并内嵌的 ZIP codec、流式 writer、严格 reader、旧 JSON 兼容桥、分批暂存、事务发布、取消/进度、直接文件句柄导出和生产 UI。`tests/e2e/zip-capacity.spec.js` 提供 100 张真实 PNG 的容量往返用例，并可手动设置 300 张规模；用例存在不等于本次已运行或已通过相应规模。

仍需完成的门禁：

- 通过真实生产导入器导入本规范配套的分镜/图片包与完整项目包，读回并刷新确认持久化。
- 外部 Agent 盲测：仅提供公开指南、Schema、示例、用户授权的图片和需求，不阅读源码；核对它能交付合法文件且不越过权限边界。
- iOS Safari、主屏幕 PWA、Android Chrome 与不同 origin/profile 的真实跨设备交接。
- 真实设备容量、存储配额、后台恢复、断电/刷新中断、损坏包与并发修改验收。
- 严格脚本 CSP 已合入 `main`，本功能分支已继承其 CSP 哈希构建与事件白名单；ZIP 代码和固定版本 codec 必须置于同一受哈希授权的应用脚本中。主线已完成 Chrome / Firefox / Safari 实测，本集成分支仍需 CI 三引擎回归。

250 MiB、1 GiB、ZIP64 边界或更大规模不属于当前可导入包的支持范围。在容量门禁未完成前，应把大任务拆分成多个小包；不得将理论上的 ZIP64/流式能力宣传为已验证性能。

## 7. 去重规则

先按逻辑 key 去重读取，同一 key 只读取一次；读取图片后计算标准原始字节 SHA-256。不同 key 若字节完全相同，只在归档存一份并在清单中保留所有逻辑映射；同尺寸但摘要不同的图片分别保留。不会扫描本机全库、删除本地图片或计算视觉特征。图片的尺寸和 MIME 不作为画面相似判断。
