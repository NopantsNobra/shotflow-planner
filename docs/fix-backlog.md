## FB-1 新增分镜表单：任意交互会清空已输入内容（P0 · Bug）

**现象**（管理员报告）：输入分镜名称后再点击「动作」（姿势图库分类 chip）名称被清空，必须先选动作再输名称。

**根因**（已核实，比报告范围更广）：
- `renderShots()`（1052 行起）是**全量 innerHTML 重绘**；新增表单的 `#s_name`（1080 行）与 `#s_note`（1085 行）**没有 value 绑定**，`#s_date/#s_slot/#s_dur/#s_scene`（1081-1084 行）只有默认值——任何触发重绘的交互都会把未提交输入重置。
- 触发重绘的交互至少有三处：
  - `setShiseiCat(cat)` 1108 行（点击姿势图库分类 chip，即「动作」）
  - `toggleRef(id)` 1109-1114 行（点击任意参考图，含我的素材与图库）——**选参考图同样清空名称/备注**
  - 同步引擎完成后的重绘钩子 1898 行（`view.tab==='shots'` 时 `renderShots`）
- 对比：`#s_filter`（1089 行）有 `value="'+esc(view.shotFilter)+'"` 绑定，所以搜索框不丢字——证明重绘架构下表单值必须显式回填。

**预期行为**：名称、备注、日期、时段、时长、场景六个字段与「选参考图 / 切分类 chip / 图库同步完成」三类操作完全正交；任意操作顺序均不丢失已填写内容；点「添加分镜」成功后才清空表单。

**建议方案**（二选一，倾向 B）：
- A（小改）：表单草稿提升到 `view.shotDraft={name,note,date,slot,dur,scene}`，输入 `onchange` 写入 draft，`renderShots` 重绘时回填 `value`；`addShot()` 成功后清 draft。
- B（彻底，推荐）：沿用 v6 `renderMoodGrid` 的局部重绘模式——表单区、图库区、分镜列表拆为三个独立容器，`toggleRef/setShiseiCat/同步钩子` 只重绘图库与列表，**表单区仅在进入页面时构建一次**。同时修掉 1898 行同步钩子的全量重绘。

**验收要点**：输名称→切分类 chip→名称仍在；输名称→选 3 张参考图→名称仍在；改日期→选参考图→日期保持用户值（不回退默认）；添加成功后表单按预期清空；现有拖拽排序、3 张上限、`selRefs` 行为不变；`tests/logic.test.mjs` 44 项不回归。

## FB-2 分镜页缺「上传图片 / 本地图片」入口（P1 · 功能缺口）

**现象**：分镜页参考图选择器只有两组来源——「我的素材」（情绪板已有图，1063-1068 行）与「姿势图库」（shisei 同步，1069-1076 行）；用户想用自己的新图，必须切到情绪板页上传再回来。

**根因**：设计上参考图统一取自情绪板，分镜页未提供入口；且 `addMoodImg`（1028 行）**强依赖情绪板页的 `#m_tag` 输入框**（1030 行 `gv('m_tag')`），直接把上传按钮搬进分镜页会因 `m_tag` 不存在而抛错。

**预期行为**：在参考图选择器顶部提供「上传图片」按钮（`accept="image/*"`，即"从本地打开"）；选择文件后走现有压缩链路（800px / JPEG .72 / IndexedDB）入库到情绪板，并**立即出现在可选列表中**（最好直接自动勾选为当前分镜参考图）；上传时可顺带输入标签（复用 `parseTagsInput`；无标签输入框时应提供轻量输入或允许后补），`gv('m_tag')` 的强依赖需在此过程中解耦（改为参数传入）。

**验收要点**：分镜页上传→新图出现在「我的素材」并可立即勾选；上传的图在情绪板可见、可打标签；压缩与 IndexedDB 行为与情绪板上传一致；`addMoodImg` 在两处入口下都不抛错；一次多选文件可不支持（保持单张，与现状一致）。

## FB-3 已创建分镜的参考图操作：添加 / 查看大图 / 删除 / 更换（P1 · 功能缺口）

**现象**：已创建分镜的参考图（1094-1099 行）只是**静态缩略图展示**：无图显示「无参考图」纯文字；有图不可点击、不可删、不可换。当前 `refIds` 只能在**新增**分镜时通过 `selRefs` 一次性选定，创建后无法修改——这是比「操作入口」更深的缺口：**分镜参考图编辑能力整体缺失**。

**预期行为**：
- 无参考图：「无参考图」占位变为可点入口「+ 添加参考图」（进入该分镜的选图态：高亮/滚动到参考图选择器，或弹出选择面板），选图直接写入该分镜 `refIds`（仍受 3 张上限约束）。
- 有参考图：点缩略图打开**大图查看**（灯箱/模态层，含原图；`shisei:` 占位图不可看大图则禁用入口）；缩略图 hover 提供两个操作——**删除**（从该分镜 `refIds` 移除该图，不影响情绪板原图与其它分镜）与**更换**（进入选图态，新选图替换指定位置，保持顺序）。
- 编辑过程中的 `selRefs` 语义需扩展或引入「编辑目标分镜 id」状态，避免与新增表单的选图互相污染。

**根因**：`refHtml` 为纯展示；`toggleRef/selRefs` 仅服务新增表单；无分镜级 refIds 编辑函数。

**验收要点**：四类操作均只改目标分镜的 `refIds`，不产生新分镜、不动情绪板数据；删除后重绘正确、拖拽排序与时间冲突标记不受影响；shisei 占位图（图库被清除后）的大图入口禁用且有提示；`refIds` 上限 3 张在编辑路径同样生效；导出/提案/拍摄日模式中引用关系保持正确。

## FB-4 页签分组层级不清（P2 · 视觉/交互）

**现象**（截图证实）：`策划 | 概念 情绪板 | 执行 | 分镜 日程 清单 | 落地 | 预算 协作` 中，分组词（策划/执行/落地，`tab-group`，853-855 行渲染，CSS 132 行 10px 浅灰）与功能页签横向混排、字号仅差 3px，用户会把「策划」误读为与「概念」同级的页签。移动端当前直接隐藏分组词（288 行），层级信息完全丢失。

**预期行为**：分组与页签的归属关系一眼可辨。三个候选方案（建议按 B 落地，A 列为备选）：
- A（彻底）：二级导航——顶部先选「策划 / 执行 / 落地」三个组，组内再显页签；信息架构最清晰，但多一次点击。
- B（推荐）：保持单行，但**视觉分层**——分组词改为带浅色底的小块/竖排侧标（与页签明显异质），组与组之间加分隔线，当前激活页签所属组的分组词同步强调（加深色/加粗）；移动端不再隐藏分组词，改为组内横滚。
- C（最小）：页签文案加角标（如「概念 · 策划」）——不推荐，信息噪音大。

**验收要点**：截图对比可明确辨析层级；移动端分组信息不丢失且不引入横向错乱；页签切换行为与 7 页签结构不变；`tests` 不回归。

### 背景：管理员给的参考站
`https://posewear.pages.dev/#pose`（衣姿 PoseWear）。管理员原话：它虽是为后续生成图片设置的前置，但「前面这些动作和衣服也很有参考价值」，问能否作为额外动作设计挂载。

### 已核实的事实（来源：网站页脚「来源与致谢」、页面源码、meta 描述）
- **规模**：98 组姿势 / 490 张角度图、1,068 套服装、1,499 张人像参考图
- **7 个页签**：姿势 / 深度姿势 / 服装 / 人像 / 试穿 / 收藏 / 最近
- **姿势分类**：可爱、坐姿、站姿、跪立、躺卧、侧坐·鸭子坐、蹲姿、前倾、后仰、扭身（每组 5 角度：正面/俯拍/仰拍/侧面/斜侧，中英文描述）
- **服装分类**：春季、夏季、秋季、冬季、派对礼服、泳装、按单品和颜色
- **人像分类**：正脸、生活照、短发、中长发、半长发、长发
- **组合能力**：姿势 + 服装 → 组合提示词（中/英切换）；收藏可导出/导入；在线 AI 试穿；配置图像模型 API Key 生成
- **来源声明**：姿势/服装来自 `@giaaibusi` 的 AI Pose Gallery / AI Costume Gallery；人像来自 `@agi_aibusi` 的 AI Portrait Gallery（**CC0 1.0**：可商用、可修改、无需署名，但原作者希望不要原样批量转载）；深度姿势热链自 `ai-pose-depth-gallery.pages.dev`（非官方汉化，**图片不经本站**，对方能看到 IP）；中文名称与描述为 PoseWear 自行翻译
- **开源**：`github.com/atuizz/posewear`

### 关键判断（决策记录）
1. **不是同源，不能复用现有同步通道**。本工具 `shotflow.html:461,464` 致谢的是 `wquguru/shisei` 与 `HRuiCcc/RuiC-PoseAtlas`；PoseWear 上游是 `@giaaibusi` 的 Gallery 系列。作者、仓库、数据形态都不同（shisei 是单人线稿/姿势，键 `shisei:<pid>:<view>`；PoseWear 是每姿势 5 机位角度的成组参考图）。**结论：单接一路同步，独立 object store，不混进 `shisei_meta`/`shisei_images`。**（管理员 2026-11-20 拍板）
2. **值得借的是「维度 + 组合逻辑」，不只是词表**：姿势×角度、服装、发型的分类，以及「选中 → 生成中英双语组合描述 → 用到下游」的链路。本工具现有分镜只有 `position`（机位）+ `light`（光线），缺姿势/服装/发型维度，也缺面向 AI 出图的提示词输出。
3. **不内置图库热链、不做在线试穿、不接图像模型 API**：超出摄影策划工具边界；深度姿势热链会暴露用户 IP；姿势/服装的转载许可未像人像那样明确 CC0。
4. **挂载形态**：挂在分镜页（不新增第 8 个页签，7 页签分组已稳定）；选中后写入分镜数据，参考图仍走现有 `p.refs` 链路（用户上传/选图），PoseWear 图作为独立同步源供参考。
5. **分支策略**：开 `feature/posewear-sync`，设计稳定前不并入 main（main = 线上内容）。暂不开 PR：单人仓库无 reviewer，PR 审查价值为零；部署从本地目录直接推，PR 不参与链路；讨论留痕放本文件比 PR 描述持久。需要逐行讨论时再开。

### 管理员决定（2026-11-20 已确认，不要再当待定项讨论）
- **A — 客户可见物料**：管理员原话「这些图本来就不进客户可见物料，这是动作参考，给我（拍摄者）看的」，并补充「手册就是我看的，不是客户看的，可以进」。⇒ **客户可见物料 = 客户提案（含导出的提案 HTML）**；中英文描述与 PW 图**不进客户提案**，但在 shot 快照 + `#pwPanel` 界面展示/可复制，**允许进执行手册**（内部物料）。客户提案导出物保持与基线完全一致。
- **B — 词表范围**：管理员原话「不精简，不排除成人向的」「不配套 18+ 开关，动作姿势本来就没有必要做这个分类」。⇒ 选定「**全量内置，无 18+ 开关**」：放开 `a:1` 类目（内衣/性感/性感·大胆/全身·性感/双人互动），分类词表补齐；**不引入年龄确认弹窗/开关/默认隐藏机制**，导入过滤同步放开。成人向类目与其他类目一视同仁展示，不加任何特殊标记。
- **C — 图片进执行手册参考列**：管理员原话「可以」。⇒ 选定「**进手册**」：在 shot 上增加 `pwPrintKeys:string[]`（存 `posewear:` key），手册参考图列按 key 取图打印；打印前 dataURL 内联，注意 112px 尺寸、分页与体积。
- **A 与 C 的边界（2026-11-20 二次澄清后定稿）**：客户可见 = 客户提案；执行手册 = 管理员自己看的内部物料。⇒ **`promptZh/promptEn`（中英描述）与 `pwPrintKeys`（PW 参考图）都允许进执行手册**，但两者**都不进客户提案**。实现时严格按文档类型分支，不要把「不进客户提案」误做成「不进任何导出文档」。
