# Stillmark 资产包容器规范 · 设计基线

日期：2026-11-26。状态：产品要求已确认；容器与容量实现尚待开发验证。本文定义设计方向、v1 拟议交换契约和验收，不表示应用已支持 ZIP。
来源：用户明确要求为大量参考图及未来资产增长预留余量；取代此前“JSON 优先、必要时 ZIP”的路线。

## 1. 核心决策

- 正式的新迁移载体为标准 ZIP，建议文件名 *.stillmark.zip（可被通用 ZIP 工具解包；不得依赖私有压缩格式）。JSON 仅承载元数据和摄影业务结构，不嵌入 Base64 图片。保留旧版 v1–v4 JSON 导入；开发分支 v5 JSON 原型只用于验证选择、依赖、追加语义，未正式发布，不将其当作新的长期契约。
- 容器版本 containerVersion、业务数据版本 dataVersion、业务意图 kind 分离；独立于应用版本和 IndexedDB schema。支持已知版本；不识别的主版本或必需能力明确拒绝，不降级到整库恢复。
- 首发覆盖新项目包（完整或部分项目），随后按原有意图支持收藏复用和整库备份；整库恢复必须由明确的独立类型与确认触发。当前 JSON 全量备份不立即删除。
- 容器格式与本地存储实现隔离，不要求重写所有项目或提前迁移数据库。不依赖账号、云同步、联网、Agent API。

## 2. ZIP 文件布局（拟议 v1）

```text
session.stillmark.zip
├── manifest.json
├── data.json
└── images/
    ├── <sha256>.jpg
    ├── <sha256>.png
    └── <sha256>.webp
```

manifest.json 保存 format="stillmark.asset-pack"、containerVersion=1、dataVersion、kind、exportedAt、data 描述（path、bytes、sha256）及 images 列表（每个逻辑 key、path、bytes、sha256、mime）。可有可选来源与统计字段；不得包含 API key 或设备标识。data.json 复用已验证的项目数据模型和追加语义；项目引用仍使用逻辑图片 key，不绑定 ZIP 路径或运行时 IndexedDB key。清单 kind 与数据类型必须一致。正式 schema、样例与生产校验器在 PORT-2a 同批完成，不将本节草案视作已发布 schema。

图片按原有合法 MIME 保留已存储二进制内容，不为导出再次有损压缩。相同字节共享内容摘要及唯一 ZIP 条目；不同逻辑 key 可映射到同一图片条目。摘要同时校验数据和图片字节，不是签名、不提供真实性或加密。ZIP 自带 CRC 也应检查。JPEG、PNG、WebP 等现有支持的栅格类型优先；旧内置示例 SVG 兼容问题需单独处理，禁止任意 SVG/HTML/脚本。未来如有原图、缩略图、附件或派生文件需求，扩展资源类型/角色及版本，不破坏已有引用语义；未支持的附件不自动执行/展示。

## 3. 处理架构：业务与容器分离

```text
用户选择项目/分镜/素材
       ↓
业务选择与依赖闭包（复用现有代码）
       ↓
Transfer model：结构化数据 + 逻辑资源描述
       ↓
Archive writer / reader（ZIP / 旧 JSON 适配）
       ↓
逐条验证、分批暂存 → 预览、确认 → 事务提交
       ↓
现有项目/图片存储与写入守卫
```

- 选择成熟的 ZIP 库并固定版本、记录许可证与上游来源；评估 zip.js 等支持流式 I/O 和 ZIP64 的实现。先做独立验证：单文件构建（库内嵌，无 CDN/运行时联网）、file://、HTTPS/PWA、严格 CSP、iOS Safari。不要自行实现不完整的 ZIP 解压器，不为了引入库放宽 CSP。Worker 是可选优化，非必需条件。
- 普通 JPEG/PNG/WebP 已压缩，优先 STORE（无二次压缩），JSON 可 DEFLATE。支持流式写出到用户授权的文件句柄（能力检测）；不支持的浏览器以 Blob/下载/系统分享为降级路径，明确相应容量限制；不得声称所有浏览器均可零内存流式保存。
- 读取先解析目录与小清单，校验元信息和大小，再逐条读取、校验、解码、暂存，限制并发与解压实际字节，避免一次将全包转为文本或构造巨大 data URL 对象。进度、取消与失败清理是用户体验的一部分。
- 现有 images store 仍含 data URL，首批可逐图转换，避免同时驻留大量 Base64。大包真正落盘不能只将 ZIP 换成全量解压到 JS 对象；后续使用暂存区、批次或 Blob 存储适配器。新图片暂存不可被正式项目读取或普通回收删除；确认后以可恢复的原子发布连接项目和资源，失败/取消/异常重启清理未提交暂存。完整备份、旧客户端兼容与并发写入须实测；如引入新 store 或 Blob 类型，另行设计 DB 迁移，不默默改变已有读写契约。
- 导入预览展示类型、项目/分镜数、图片数、体积、目标、重复提示、缺失/隐私风险；拒绝前不写正式数据。正式提交前复核持久化基线，保留现有项目和草稿。已缓存姿势图只按所选引用打包且遵守许可，不把整个图库带走。

## 4. 非可信归档与安全边界

- 白名单根路径与条目类型，拒绝绝对路径、..、反斜线、NUL、重复或归一化冲突路径、符号链接、加密/不支持的压缩方法、嵌套归档与非预期可执行内容。禁止按归档文件名写任意本地路径。
- 文件头、目录、清单、实际解压计数、字节数、CRC 与摘要交叉验证；拒绝未声明、缺失及重复逻辑 key、数据引用悬空、图片格式与内容不符、超过配额、压缩炸弹及异常超长清单。元信息声明不能替代实际计数；限制条目数、单图字节、总解压字节、像素尺寸及处理时间。
- 清单/数据仅解析为数据，转义显示；不执行包内内容。导入默认追加，未知类型拒绝。显式整库替换需独立确认与备份提示。
- ZIP 本身不加密；传输、分享和保密仍由用户决定；未来加密需单独评估，不自行发明密码协议。

## 5. 容量与验收（目标而非当前支持承诺）

格式本身不固定图片数量或按设备设置永久容量上限；容器选型预留 ZIP64（超过 4 GiB/65535 条目的扩展）和流式 I/O 能力，但 v1 是否接受 ZIP64 由实测决定，不能把理论能力当作浏览器实际承载能力。首版运行时根据实际测试设明确安全上限，可配置/渐进提高；不得为绕过限制牺牲校验或数据完整性。

| 场景 | 初始验收目标 |
|---|---|
| 小包 | 单分镜/单图，数个项目；离线往返，图片与关系逐字节/语义一致 |
| 常用包 | 100–300 张参考图，25–100 MiB 级；真实移动端导入/导出、进度与取消 |
| 大包 | 500–1000 张参考图、250 MiB 级；桌面完整往返、移动端分批处理实测，明确降级/拒绝边界 |
| 余量压测 | 1 GiB 级桌面文件、ZIP64 边界独立合成测试；验证无 O(总图片载荷) Base64 常驻，不将其作为首版手机承诺 |
| 故障 | 磁盘/IDB 配额、损坏 ZIP、伪造大小、重复路径、断电/刷新、并发修改；原项目完好、可恢复/清理 |

记录实际压缩前后字节数、耗时、峰值内存（支持时测量，不支持则明确）、首次进度反馈、取消延迟、重复导入和事务恢复。跨设备测试须含干净 iOS Safari / PWA、Android Chrome 与桌面三引擎。大包未达到移动验收门槛时，先保留分批小包的明确路径，而不是宣称全面支持。

## 6. 实施顺序

1. 保留 PORT-1 的选择、依赖和安全追加语义，隔离容器编解码接口；未发布的 v5 JSON 输出仅用于分支开发验证。
2. PORT-2a：ZIP 库/许可证/CSP/文件能力验证，正式 manifest/data schema、归档生成与读取、小包导入导出、旧 JSON 回归。
3. PORT-2b：渐进式暂存、原子发布及异常回收、进度/取消和容量/安全测试；确保真实移动端达到可接受的预算。
4. PORT-1b 与 AGENT-1：指定项目追加、预览、正式契约及可验证 ZIP 示例。Agent 可用任意标准 ZIP 工具生成，不能依赖应用内模型服务。
5. AGENT-2：真实 Agent 盲测、跨设备往返；完成发布验收再将 ZIP 作为默认新迁移出口。旧版 JSON 读入继续保留。

## 7. 开发分支候选 schema（未发布）

- `schemas/asset-archive-manifest-v1.schema.json` 与 `schemas/asset-archive-data-v1.schema.json` 直接对应应用内 schema 定义；逻辑测试防止漂移。首期 kind 取 projects 或 shots，dataVersion 为 1；data.json 只含 dataVersion、kind、entries，不包含 Base64。后续复用素材和整库恢复使用不同 kind，暂不识别。
- 清单逻辑键唯一，允许多个键共享同一内容摘要/条目，文件路径必须按 SHA-256 和 MIME 构造；同摘要的大小/MIME 不一致则拒绝。清单与业务类型、引用闭包必须一致。
- 初始 Blob 原型运行时暂设 128 MiB 归档/展开预算、16 MiB 单图/业务数据预算、4 MiB 清单预算、10000 唯一条目、20000 逻辑图片映射；这些是尚待压测调整的安全门禁，不是格式永久限制或已验证支持能力。清单验证不等于真实解压字节/CRC/摘要校验，后者由后续 archive reader 实现。真实 ZIP 仍未接入生产导入器。

## 8. 精确去重实现决策（管理员补充）

参考 [理巢 NetTidy duplicate.py](https://github.com/NopantsNobra/NetTidy/blob/main/nesttidy/duplicate.py) 的大小分组、首尾采样、全文复核思路；本项目归档时必须读取图片字节并生成标准 SHA-256，因此直接复用完整性摘要，避免额外采样、图像解码或视觉特征计算。逻辑引用 key 去重在读取前完成；不同 key 若字节一致仅写一次，保留所有逻辑映射；相同大小但不同摘要各自保留，不合并近似画面。不得删除用户本地图片，也不触发全库扫描。仅记录唯一摘要描述与资源统计，逐张读取，流式写入，不保留全包 Base64 对象。标准摘要为原始文件字节 SHA-256，不采用理巢内部 size 前缀口径。新增候选 writer 与严格 CSP 探测回归覆盖重复 key、异 key 相同字节、同尺寸不同内容、预算超限中止；实际 UI/reader/暂存尚待接入和验证。

## 9. 归档读取器候选实现

独立 reader 先对目录/声明大小、精确 ASCII 白名单路径、重复/加密/符号链接/非 STORE 或 DEFLATE 条目进行拒绝，再逐条限定输出大小、CRC/本地头/重叠检查，校验 manifest 与 data 摘要及依赖闭包。预览阶段不读取图片字节；确认后 consumeImages 一次性会话逐个唯一文件校验二进制签名及 SHA-256，再向暂存层交付 Blob 与全部逻辑 key。图片签名只作轻量格式初筛，不等同完整解码与像素预算检查；后续暂存/应用层补全。未接入 UI 或数据库提交，不能宣称 ZIP 导入已经交付。严格 CSP 探测新增正常消费、错误摘要、额外条目、预算超限与错图片字节回归。

## 10. 暂存与原子发布候选实现

复用 v4 images store 的独立数组键命名空间，正式图片仍为字符串 key；暂存写入逐张提交，发布时在 projects/images 同一事务内比较基线、逐张读暂存/add 正式图片/删除暂存，最后写项目。任何碰撞、缺失、事务失败回滚；失败或取消按会话清理，过期租约 24 小时后回收。无需 DB schema 升级；旧版清库仍可删除暂存并使发布安全失败。当前尚未接入 UI，验收以 CI 与后续端到端测试为准。

## 11. UI 接入和运行时边界

项目与分镜批选默认输出 ZIP（旧 JSON 仍可导入）；预检阶段不写项目/图片，确认后逐个唯一文件校验并逐逻辑 key 暂存，保留原有参考图标签/关系。归档内去重不会合并本地逻辑身份，因此对逻辑引用展开体积同样设置预算（128 MiB），写入器与读取器对称拒绝超限。取消信号传入 ZIP 库；正式事务阶段禁用取消。目录单次读取限制 8 MiB，图片 header 尺寸校验限制 40 MP / 单边 16384，轻量识别而非视觉模型或完整解码。AVIF 需可识别的 ispe 元数据；无法确认尺寸的图拒绝，旧内置精确模板 SVG 可转换为 PNG。当前 Blob 路径仍有全量二进制输出驻留，容量压测与文件句柄直写待后续验证。

## 12. 文件句柄直写

支持 File System Access API 且处于安全上下文时，项目/分镜批选额外显示「直接保存到文件」。用户点击后同步请求保存目标，ZIP writer 将分块直接交给 createWritable，不构造全包 Blob；浏览器不支持时继续使用普通 ZIP 下载。取消选择不开始归档，失败不暗中改走下载；writer 在异常时 abort，成功 close 才发布文件。仍沿用 128 MiB 保守预算，暂不依据理论流式能力放宽容量；真实文件句柄、移动设备与大包验收另行测试。

## 13. 容量自动化回归

`tests/e2e/zip-capacity.spec.js` 使用确定性逐张生成的真实 384×256 PNG（非填充假文件），默认 100 张唯一图及 1 个重复逻辑 key，约 25–35 MiB；走实际 writer、导入预览、暂存及原子发布，抽样复核 SHA-256、刷新持久性、暂存清理和冷图片未进入 imgCache。日志 `[ZIP-CAPACITY]` 记录归档字节、写入/预检/导入耗时和最大写入块，不把 JS heap 指标当作浏览器全进程峰值内存。可用 `ZIP_SCALE_COUNT=300 E2E_BROWSERS=chromium npx playwright test tests/e2e/zip-capacity.spec.js` 运行约 90 MiB 压测；这是测试入口，尚非已验证的 300 图成绩。默认 CI 三引擎 100 图回归；真实手机与 250 MiB 及更大容量仍待验证。
