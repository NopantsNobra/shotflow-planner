> 依据：`竞品调研与升级方案.md`（G1–G11 及 §8/§9 对账）、`docs/backlog.md`、`docs/system_design.md`、`docs/settings-design.md` §8、README §七、当前代码实测。

## 一、版本主张（先给结论）

**v11 定位为「数据安全与结构治理」版本，不追功能面扩张。**

理由不是"该还技术债了"这种泛泛判断，而是 v10 累积的复杂度已经把三个原本的后备项变成了产品风险：

1. **B2 多标签页并发覆盖是真实的数据丢失路径**——不是提示不友好，是 A 页的编辑可能静默抹掉 B 页的成果。产品定位是"本地优先、数据只在你设备上"，这条不成立会直接击穿信任。
2. **B4 无 CSP + 大量内联 handler**——v10.7.1 刚补过存储型 XSS 注入面，防守只有一层转义。注入面一旦回归即完全可利用，属于底线缺口。
3. **C2 关键路径无 E2E**——v10 有统一排程、多日、自动跨日 7 轮、capHit 兜底、导入净化等复杂规则，但多日拍摄、自动跨日、导入导出、删除撤销、拍摄日模式、拖拽排序全靠逻辑测试与手工点击。复杂度上去了，回归网没跟上。

三者的共同特征：**用户看不见新按钮，但一旦出问题就是灾难性的**。这比再做一个模板功能优先级更高。

用户可见的产品价值（P3-11 项目模板、P2-10 光线增强）放 v11 的可选轨道，不进主线；需要重定位的 P2-9 分享协作不进 v11——见第六节。

## 二、范围与优先级

### P0 · 必须做（版本主线）

| 项 | 内容 | 为什么是 P0 | 验收 |
|---|---|---|---|
| **B2** | 多标签页并发写覆盖 | 数据丢失路径 | `BroadcastChannel`（降级 `storage` 事件）+ 写前 `updatedAt` 版本比对；双开编辑不同项目，任一页保存后另一页**不覆盖**且收到"另一标签页已修改"提示；冲突合并策略明确（提示而非静默丢）。**不能只做提示不做防护。** |
| **B4** | CSP 与内联 handler | 注入防线只有一层 | 阶段一：`object-src 'none'; base-uri 'self'; form-action 'none'`，**在 `file://` 下不阻断运行**（硬需求）；阶段二：内联 `onclick` 迁事件委托后再收紧 `script-src`。验收含 `file://` 与 HTTPS 双环境实测。 |
| **C2** | 关键路径 E2E | 复杂排程无回归网 | 补齐 6 类缺口：多日拍摄、自动跨日（含 7 轮上限）、导入导出往返、删除撤销、拍摄日模式、拖拽排序。要求断言数据层结果与 DOM 表现，不只点按钮不报错。 |

### 可选轨道（管理员决策后才进）

## 四、需管理员裁决的开放项

这些是**产品决策，不是待办 ticket**，我不替你定：

1. **v11 是否要用户可见亮点？** 若要，选 P3-11 模板复用还是 P2-10 光线增强；若不要，v11 就是纯治理版本，发布说明要如实写"无新功能"。
2. **跨项目全局词表是否立项？** `settings-design.md` §8-⑥ 明确它是新需求（要改变数据归属与合并规则），不是设置页补个按钮。当前项目级 `p.tagVocab` 模型是否继续，需要你拍板。
3. **P2-9 只读分享 / 客户批注闭环是否重开定位讨论？** 调研限定"定位不变则维持导出交接"。它涉及后端或第三方存储、鉴权与隐私，会改变"无后端"的产品前提——不进 v11 开发排期，只做决策记录。
4. **SW 版本真源方案是否维持现状？** 当前用 `MODULE_VERSIONS.swCache` 硬编码 + `verify-version` 防漂移，未做 `postMessage` 运行时读取（`settings-design.md` §8-②）。我的判断是**维持现状即可**——运行时读取带来的复杂度高于收益，除非有实测漂移事故。
5. **PoseWear 禁令是否维持？** 我的建议是维持，直到三个具体故障的操作路径被记录并复现。

## 五、执行顺序建议（不承诺工期）

1. **先 C2**：给复杂排程补 E2E 网。后续 B2/C3 改动都依赖它兜底，先做省大量手工回归。
2. **再 B2**：并发写防护 + 冲突提示，配套双标签 E2E。
3. **再 B4 阶段一 + C4/C6**：低风险治理，可与 B2 并行但各自独立验收。
4. **然后 C3 拆段**：结构变化最大，放在回归网完备后做。
5. **B4 阶段二（事件委托 + 收紧 script-src）**：依赖 C3 拆段后的结构，放最后。
6. **B6 / B1 / 可选轨道**：按第四节裁决结果插入。

## 六、风险与边界

- **B2 的难点不是代码量，是合并语义**：两个标签页都改了同一项目时，"提示后谁赢"必须明确。建议策略是后写者被拒并提示刷新，而不是自动合并——自动合并对这种单 key 整存结构风险更高。
- **B4 的硬约束是 `file://`**：CSP 在该协议下行为与 HTTP 不同，任何收紧都必须双环境实测，不能只验线上。
- **C3 拆段不能变成重写**：现有 `verify-build` 逐字节门禁是保证产物与源码同源的关键，拆段后必须继续通过；禁止借拆段顺手改行为。
- **不设工期承诺**：本文件只排优先级与依赖，不给时间估算；实际节奏由管理员决定。
